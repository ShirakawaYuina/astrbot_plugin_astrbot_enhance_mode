# 群聊回复上下文消息边界设计

## 背景与问题

插件当前在收到群消息后，先把本轮消息写入 `RuntimeState.session_chats`，再在
`on_llm_request` 阶段读取整个共享历史。React 模式随后又把 `req.prompt` 作为
“新消息”拼入提示词，导致当前消息在同一次模型请求中出现两次。

此外，同一群聊中的后续消息可以在当前请求等待会话锁期间继续写入共享历史。
因此，请求真正进入 `on_llm_request` 时读取到的历史可能已经包含当前消息之后到达
的内容。简单删除历史最后一条无法解决问题，因为最后一条未必是当前请求对应的消息。

引用回复还会把被引用消息的全文再次写入历史。若原消息仍在历史窗口中，模型会同时
看到原消息和引用副本，进一步放大“复读”的错误判断。

## 目标

1. 普通被唤醒回复和 `probability` 主动回复只接收当前消息之前的群聊历史。
2. 当前消息作为独立且唯一的回复目标出现，并携带昵称、用户 ID、时间和消息 ID。
3. 当前消息之后到达的消息不得进入本轮模型请求。
4. 模型仍可根据当前消息 ID 输出正确的 `<quote id="..."/>`。
5. `model_choice` 主动回复继续读取触发判定时可见的完整候选历史，自行选择回复对象。
6. 引用目标仍在历史窗口时只记录引用消息 ID，避免再次嵌入全文；目标不在历史窗口时保留引用文本。
7. 无法建立可靠消息边界时清晰暴露错误，不静默退化为完整历史或猜测边界。

## 方案比较

### 方案一：删除历史最后一条

实现最少，但无法处理并发到达的后续消息。当前请求等待期间若消息 B、C 已进入历史，
删除最后一条只会删除 C，当前消息 A 仍然重复，消息 B 也会错误泄漏进 A 的请求。

### 方案二：在记录消息时复制一次完整快照

能够隔离后续消息，但需要把快照附着到事件或维护额外的按请求状态。事件可能在多个
处理阶段间传递，额外快照还会复制最多数百条历史，增加状态和内存管理复杂度。

### 方案三：在请求阶段按当前消息 ID 截断（采用）

历史记录已经包含稳定的 `#msg{message_id}` 标记。请求阶段在共享历史中定位当前
消息，取其前方内容作为历史，并把命中的当前消息单独作为回复目标。该方案无需长期
保存请求快照，也能排除所有后续消息，并与现有图片消息注册表的消息 ID 体系一致。

## 组件设计

### 结构化历史边界结果

新增一个小型不可变数据结构，表达一次边界解析的结果：

- `history_lines`：严格位于当前消息之前的历史行。
- `current_message_line`：与当前消息 ID 对应的完整历史行。

边界解析实现为独立纯函数或静态方法，输入历史行列表和当前消息 ID，输出上述结果。
它从后向前查找消息 ID，以便在异常重复记录同一平台消息时使用最近一次记录。

如果当前消息 ID 为空，或历史中找不到对应记录，解析函数抛出明确异常。调用方记录
origin、message ID 和历史长度后终止本次上下文注入。不得使用完整历史、最后一条消息
或原始 prompt 猜测边界。

### 当前回复目标

普通被唤醒回复和 `probability` 主动回复使用以下逻辑结构：

```text
Chat history before the current message:
<仅包含当前消息之前的历史；为空时使用明确的空历史标记>

Current message to reply to:
<当前消息完整历史行，包含 #msgID>

Reply to the current message above.
```

模型只看到一次当前消息，同时保留生成引用标签所需的消息 ID。`req.contexts` 继续清空，
避免 AstrBot 对话历史与插件群聊历史混合。

### model_choice 主动回复

`model_choice` 的语义是从最近候选消息中自行挑选回复对象，因此不把某条消息指定为
唯一当前目标。该分支继续使用触发时可见的群聊历史，但历史必须在进入 LLM 请求时复制
为局部列表，再执行长度约束，保证提示词构造期间不受共享列表后续变更影响。

### 非 React 模式

群聊历史增强依赖 React 模式，但代码仍保留非 React 分支。该分支同样按当前消息 ID
截断后，只把当前消息之前的历史追加到 system prompt；当前消息仍由 AstrBot 原始
`req.prompt` 传递。这样即使配置组合异常，也不会重新引入当前消息重复或未来消息泄漏。

### 引用文本去重

记录一条带 `Reply` 组件的消息时：

- 若引用目标消息 ID 当前仍存在于该会话历史中，写入 `[Quote #msgID]`。
- 若引用目标不存在于当前历史窗口，写入 `[Quote #msgID 昵称: 引用文本]`，保留模型
  理解引用所需的信息。
- 若平台没有提供引用目标 ID，继续保留昵称和引用文本，因为无法建立可靠关联。

该判断只读取当前 origin 的历史，不跨群聊查找。

## 数据流

1. 群消息进入 `on_group_message`。
2. `_record_message` 使用平台消息 ID 格式化并追加消息。
3. 后续消息可以继续进入共享历史，不阻塞记录流程。
4. 当前请求进入 `inject_group_context` 后，以 `event.message_obj.message_id` 定位边界。
5. 普通/概率分支取得边界之前的历史和独立当前目标；边界之后的消息被排除。
6. 历史文本经过现有 `bounded_chat_history_text` 约束后写入请求。
7. 模型针对唯一的 `Current message to reply to` 生成回复和可选引用标签。

## 错误与日志

- 缺少当前消息 ID：记录 error，包含 origin 与历史长度，停止本次上下文注入。
- 当前消息不在历史中：记录 error，包含 origin、message ID 与历史长度，停止本次上下文注入。
- 不添加按文本匹配、最后一条猜测或完整历史回退。
- 正常 debug 日志增加边界前历史条数和边界后被排除条数，便于验证并发场景。

## 测试设计

新增针对上下文边界和引用格式的测试：

1. 历史为 `[旧消息, 当前消息]` 时，旧消息进入历史，当前消息只进入当前目标。
2. 历史为 `[旧消息, 当前消息, 后续消息 B, 后续消息 C]` 时，B、C 不进入请求。
3. 相同消息 ID 异常出现两次时，使用最后一次记录作为边界。
4. 当前消息 ID 缺失或无法找到时抛出明确异常。
5. 非 React 分支只注入当前消息之前的历史。
6. 引用目标仍在历史时只写入引用 ID。
7. 引用目标已被裁剪或没有 ID 时保留引用文本。
8. `model_choice` 分支仍可看到完整候选历史，并不会被普通回复边界逻辑截断。
9. 最终普通回复 prompt 中，当前消息正文和 `#msgID` 均只出现一次。

## 验收标准

- 任意普通群聊回复中，当前消息在最终 prompt 只出现一次。
- 等待请求期间到达的后续消息不出现在本轮 prompt。
- 当前消息仍是明确回复对象，且模型可以引用其消息 ID。
- `model_choice` 主动回复原有语义不变。
- 引用目标仍在历史时不重复携带其全文。
- 新增测试通过，既有测试无回归，ruff 格式化与检查通过。
